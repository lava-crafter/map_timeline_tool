# Map Timeline Tool 收尾维护计划

> 历史说明：本文中的常驻通知、后台定位和 Quick Add 缓存方案已被快捷设置磁贴 + 短生命周期 location 前台服务方案取代，不再代表当前实现。

## 目标

Map Timeline Tool 当前功能已经基本完整，后续不再以新增功能为主，而是进入长期维护阶段。接下来的目标是让应用适合个人长期使用，并能稳定服务少量 Google Play 用户。

本计划聚焦以下方向：

* 修复权限请求流程。
* 提高定位成功率与定位结果可解释性。
* 补充使用指引，降低误用。
* 调整 UI 颜色，形成更统一的视觉风格。
* 强化备份、导入导出、数据库迁移的可靠性。
* 轻量拆分过大的文件，降低后续维护成本。
* 为 Android 17 / API 37 做准备，但不急于直接 target 37 发布。

## 非目标

以下事项不作为本轮计划目标：

* 不继续扩展大型新功能。
* 不重写整体架构。
* 不引入复杂依赖注入框架。
* 不重做整个 UI 交互模型。
* 不把项目拆成多个 Gradle module。
* 不追求大规模商业化发布能力。
* 不为了“架构更漂亮”而改动稳定代码。

# Phase 1：权限流程修复

## 背景

当前应用启动时会主动请求定位权限，然后请求通知权限，并立即尝试显示 Quick Add 通知。这种流程不够理想：

* 用户还没理解功能就被要求授权。
* 多个权限请求容易互相干扰。
* 通知权限尚未返回时就尝试显示通知。
* 权限拒绝后的降级路径不够清楚。

## 目标

把权限请求改为“按功能触发”，并让拒绝权限后的行为可预测。

## 任务

### 1.1 拆分权限请求

将权限分为三类：

| 权限           | 用途             | 请求时机                  |
| ------------ | -------------- | --------------------- |
| Location     | 打点、地图居中、离线下载定位 | 用户执行相关操作时             |
| Notification | Quick Add 常驻通知 | 用户启用或首次使用 Quick Add 时 |
| Microphone   | 噪音记录           | 用户打开噪音采集开关时           |

### 1.2 移除启动时自动请求权限

应用启动时不再立刻请求定位或通知权限。

启动后应允许用户直接浏览已有点位、查看设置、导入导出数据。

### 1.3 定位权限 gating

以下操作前检查定位权限：

* Add point。
* Auto save point。
* Quick Add。
* 地图 Center。
* 离线地图下载页面 Center。

如果没有权限：

* 弹出权限请求。
* 如果用户拒绝，显示明确提示。
* 不影响其他功能继续使用。

### 1.4 通知权限 gating

Quick Add 通知应在以下条件满足后显示：

* Android 13 以下：通知可直接显示。
* Android 13 及以上：已获得 `POST_NOTIFICATIONS`。
* 用户拒绝通知权限时，不应反复弹窗。
* 用户可以继续使用普通手动打点。

### 1.5 麦克风权限 gating

噪音开关打开时才请求麦克风权限。

如果用户拒绝：

* 自动关闭噪音记录开关。
* 显示提示：“麦克风权限被拒绝，噪音记录保持关闭。”
* 不影响其他传感器记录。

## 验收标准

* 首次启动 app 不弹权限框。
* 点击 Add 时才请求定位权限。
* 点击地图 Center 时才请求定位权限。
* 开启噪音记录时才请求麦克风权限。
* Quick Add 通知不会在通知权限未授予时错误显示。
* 拒绝任意权限后，app 不崩溃，其他功能可继续使用。

# Phase 2：定位稳定性优化

## 背景

当前定位实现基于系统 `LocationManager`，已经有 last known、fresh、precise、best effort 等逻辑。问题是部分场景下要求过于严格，尤其是 Quick Add 和自动保存时，5 秒内拿不到 fresh precise location 就会失败。

长期使用时，“完全丢点”比“保存一个低精度点并明确标记”更糟。

## 目标

提高打点成功率，并让低精度定位结果可解释、可识别、可接受。

## 任务

### 2.1 引入 Google Play Services Location

新增 Google Fused Location Provider，但不删除现有实现。

推荐结构：

```text
LocationProvider
└── CompositeLocationProvider
    ├── GoogleFusedLocationProvider
    └── AndroidLocationProvider
```

策略：

1. 优先使用 Google Fused Location Provider。
2. 如果不可用、超时或失败，fallback 到现有 `AndroidLocationProvider`。
3. 保留现有 `LocationUtils` 作为非 Google 环境下的兜底。

### 2.2 区分定位等级

定义定位结果等级：

```text
PRECISE_FRESH
FRESH_BUT_LOW_ACCURACY
LAST_KNOWN_RECENT
LAST_KNOWN_STALE
UNAVAILABLE
```

这些等级不一定要暴露为 UI enum，但逻辑中应明确区分。

### 2.3 手动 Add 的定位策略

手动 Add 保存时：

1. 先尝试 fresh precise location。
2. 失败后尝试 best effort location。
3. 如果 best effort 精度差或时间较旧，提示用户确认。
4. 用户确认后仍可保存，但点位详情中应能看到 accuracy、fix time、provider。
5. 如果完全没有位置，则保存失败。

### 2.4 Quick Add 的定位策略

Quick Add 点击通知时：

1. 先尝试 fresh precise location。
2. 失败后尝试 best effort location。
3. 如果保存的是低精度点，应在 title 或 note 中加入轻量标记，或者通过已有 metadata 呈现。
4. 如果完全没有位置，则显示失败提示。

### 2.5 Auto save 的定位策略

Auto save 不应该因为 5 秒 precise location 失败就完全丢点。

建议：

1. 倒计时结束后尝试 fresh location。
2. 失败后 fallback 到 best effort。
3. 如果保存低精度点，在 UI 中明确显示 location quality。
4. 如果完全没有位置，才失败。

## 验收标准

* 室内弱 GPS 环境下，手动 Add 更容易成功。
* Quick Add 在后台/锁屏后点击时成功率提升。
* 低精度点不会伪装成高精度点。
* 点位详情能解释定位来源、精度和 fix time。
* 没有 Google Play Services 的设备仍可使用现有定位 fallback。

# Phase 3：使用指引和权限解释

## 背景

应用功能已经较多，但新用户可能不理解：

* 为什么要定位权限。
* 为什么 Quick Add 需要通知。
* 为什么定位有时失败。
* ZIP 备份和 CSV 导出有什么区别。
* 离线地图下载为什么不能一次下载太大。
* 噪音记录不是校准分贝。

## 目标

补充 app 内使用指引和 README 文档，让用户能长期安全使用。

## 任务

### 3.1 增加首次使用说明

可以放在 Settings Help 或 About/Help 页面中。

内容包括：

* 本 app 数据保存在本机。
* 建议定期导出 ZIP 备份。
* 位置精度受 GPS、网络、建筑物、设备传感器、省电策略影响。
* 手动 Add 和 Quick Add 都依赖定位权限。
* Quick Add 需要通知权限。
* 噪音记录需要麦克风权限，且不是校准 SPL。

### 3.2 增加权限说明

在请求权限前，尽量给出上下文说明。

建议文案：

```text
定位权限用于保存你手动记录的位置点。拒绝后仍可查看和导入导出已有数据，但不能新增带位置的点。
```

```text
通知权限仅用于显示 Quick Add 常驻通知，方便从通知栏快速记录当前位置。拒绝后仍可在 app 内手动添加点。
```

```text
麦克风权限仅用于记录 3 秒近似噪音 dBFS。不会保存音频文件。
```

### 3.3 增加备份说明

在 Backup / Restore 页面说明：

* CSV：适合表格处理，但不完整保存照片、标签、设置。
* ZIP：适合完整备份和换设备。
* KMZ/KML/GeoJSON：适合地图工具。
* 换手机前应使用 ZIP 备份。
* 导入前建议先导出当前数据。

### 3.4 增加离线地图下载说明

说明：

* 高 zoom 级别会指数级增加瓦片数量。
* 建议先下载小区域。
* 多线程下载可能触发服务器限速。
* EOX Sentinel-2 Cloudless 有非商业使用限制。
* 下载地图不等于备份点位数据。

### 3.5 更新 README

README 应同步说明：

* 当前主要支持语言。
* 权限用途。
* 数据保存位置和备份建议。
* Google Play 链接。
* 项目仓库链接。
* Android 版本兼容说明。

## 验收标准

* 用户能在 app 内理解主要权限用途。
* 用户能区分 CSV、ZIP、KML、KMZ、GeoJSON。
* README 与 app 实际功能一致。
* README 中仓库链接正确。
* 没有完整翻译的语言不应在 UI 中显得像已完整支持。

# Phase 5：备份、导入导出、数据库迁移可靠性

## 背景

这是长期使用最重要的部分。用户可以接受 UI 不完美，但不能接受数据丢失。

当前已有 ZIP、CSV、GeoJSON、KML、KMZ 导出，以及 ZIP/CSV 导入。Room 数据库已有多段 migration，但测试覆盖不足。

## 目标

确保长期使用、更新 app、换设备时数据不容易丢。

## 任务

### 5.1 开启 Room schema 导出

将 Room schema 导出打开，并把 schema 文件纳入仓库。

目标：

* 以后每次数据库版本变化都有历史 schema。
* 可以写 migration test。
* 降低 Play 发布后升级丢数据风险。

### 5.2 增加 migration tests

至少覆盖：

* 公开版本数据库到当前版本。
* version 3 -> 7。
* version 4 -> 7。
* version 5 -> 7。
* version 6 -> 7。

检查字段：

* timestamp。
* latitude / longitude。
* title / note。
* locationAccuracyMeters。
* locationFixTimeMs。
* locationProvider。
* photoPath。
* noiseDb。
* sensor fields。
* tags。
* point_tags。

### 5.3 增加 ZIP round-trip test

测试流程：

1. 创建 points、tags、point_tags、photo、settings。
2. 导出 ZIP。
3. 导入 ZIP 到空数据库。
4. 检查 point 数量、字段、tag 关联、photo path、settings。
5. 再次导出，确认结构仍可读。

### 5.4 增加 CSV import/export test

覆盖：

* 普通标题和备注。
* 多行备注。
* 逗号、引号、空字段。
* UTC timestamp。
* location metadata。
* sensor metadata。

### 5.5 增加 photo path 安全测试

覆盖：

* 普通照片文件。
* 重名照片。
* ZIP entry 中包含 `..` 的非法路径。
* 反斜杠路径。
* 空 photoPath。
* 缺失照片。

### 5.6 明确 Android 自动备份策略

当前 app 允许 Android backup。需要决定：

* 是否备份 Room 数据库。
* 是否备份 point photos。
* 是否排除 osmdroid tile cache。
* 是否备份 settings。

建议：

* 用户数据：允许备份。
* 地图 tile cache：排除。
* 临时 shared backups：排除。
* 明确 README 里说明 ZIP 备份仍然是最可靠迁移方式。

## 验收标准

* ZIP 导出导入不丢点、不丢标签、不丢照片。
* 数据库升级有测试覆盖。
* 地图缓存不会被当作重要备份数据。
* Play 更新前可以通过测试确认用户数据安全。

# Phase 7：轻量文件拆分

## 背景

`MainActivity` 当前承担太多职责。继续在里面添加权限、定位、导入导出逻辑会使维护变难。

## 目标

不重写架构，只做维护型拆分。

## 推荐拆分

### 7.1 PermissionCoordinator

职责：

* 检查定位权限。
* 请求定位权限。
* 检查通知权限。
* 请求通知权限。
* 检查麦克风权限。
* 请求麦克风权限。
* 提供权限拒绝后的 UI 提示入口。

### 7.2 LocationSavePolicy

职责：

* 决定 fresh precise / best effort / last known 是否可保存。
* 给出 location quality。
* 给 UI 提供提示文案所需信息。

### 7.3 AddPointFlowState

职责：

* Add dialog 状态。
* 倒计时。
* 暂停输入。
* pending photo。
* selected tags。
* 保存成功/失败状态。

### 7.4 ExportImportCoordinator

职责：

* CSV/GeoJSON/KML/KMZ/ZIP 导出。
* CSV/ZIP 导入。
* share backup ZIP。
* Toast 或 result message 返回。

### 7.5 保持不拆的部分

暂时不拆：

* Room data 层。
* domain usecase 层。
* export parser/writer 层。
* SettingsScreen 子页面，除非后续继续膨胀。

## 验收标准

* `MainActivity` 明显变短。
* 行为不变或只按本计划改变。
* 拆分后不引入全局状态混乱。
* 不引入大型框架。
* 每次拆分都可以独立验证。

# Phase 8：Android 17 / API 37 准备

## 背景

当前项目不是 Android 17 target 状态。后续 Google Play 短期内不一定要求 target 37，但应提前准备。

## 目标

先确保可以使用 Android 17 SDK 编译，再决定是否 target 37。

## 任务

### 8.1 升级 compileSdk 到 37

先只升级：

```kotlin
compileSdk = 37
```

保持：

```kotlin
targetSdk = 36
```

然后检查：

* 编译错误。
* lint 警告。
* Android Studio sync。
* debug build。
* release build。

### 8.2 Android 17 设备测试

测试：

* 启动 app。
* 请求定位权限。
* 手动 Add。
* Auto save。
* Quick Add。
* 地图显示。
* 切换地图源。
* 离线地图下载。
* ZIP 导出。
* ZIP 导入。
* 拍照和照片查看。
* 噪音记录。
* 深色模式。
* 语言切换。

### 8.3 targetSdk 37 预检查

在真正改成 target 37 前检查：

* 本地网络权限是否需要。
* TLS / Certificate Transparency 是否影响地图瓦片。
* native dynamic code loading 是否被依赖库触发。
* 后台 Quick Add 定位是否更容易失败。
* 通知和后台行为是否变化。
* Android 17 内存限制下大 ZIP / 大照片 / 大地图区域是否稳定。

### 8.4 决定是否 targetSdk 37

如果 Google Play 尚未要求，可以暂时不急。

推荐策略：

1. 先发布 target 36 的维护稳定版。
2. 收集自己和少量用户反馈。
3. 再开单独分支测试 target 37。
4. 确认无明显问题后发布 target 37。

## 验收标准

* compileSdk 37 可构建。
* Android 17 设备基本功能可用。
* targetSdk 37 风险清单已验证。
* 不为了追新破坏稳定版本。

# 风险优先级

## 高风险

* 数据库迁移丢数据。
* ZIP 备份导入丢照片或标签。
* Quick Add 后台定位失败。
* 权限请求流程导致用户拒绝关键权限。
* targetSdk 升级后行为变化。

## 中风险

* 离线地图下载过大导致卡顿或内存压力。
* 多语言不完整导致混合语言 UI。
* 主题颜色对比度不足。

```text
功能冻结
-> 权限更合理

-> 备份更可靠
```

完成这些之后，这个 app 就比较适合个人长期使用，也适合少量 Google Play 用户稳定使用。
